■ 概要
================================================================================
最終更新: 2026-02-07

color-processor は、ARマーカー付きテンプレートに手書きで色塗りされた絵を
スキャンし、背景を除去してカラーPNG画像として出力するブラウザベースのツール。

ファイル構成:
  - color-processor.html  ... UI（HTML/CSS）
  - color-processor.js    ... 処理ロジック（JavaScript）
  - cv.js                 ... OpenCV関連（外部）
  - aruco2.js             ... ArUcoマーカー検出ライブラリ（外部）


================================================================================
■ 処理パイプライン
================================================================================

1. 画像読み込み・ARマーカー検出
   - 入力: スキャン画像（複数可）
   - ArUcoマーカー ID 0〜3 の4つを検出
   - 6種類の前処理（元画像/コントラスト強調/シャープ化/コントラスト+シャープ/
     ブラー/ブラー+コントラスト）を自動試行
   - 4セットの適応二値化パラメータ（k=2,t=7 / k=4,t=10 / k=7,t=15 / k=10,t=20）
   - 異なる試行からの結果を統合（各IDの最良検出を組み合わせ）
   - 高解像度画像(2000px超)の場合はダウンスケール(50%/75%/25%)でも再試行
   - 未検出マーカーのコーナー領域を切り出して個別検出（Phase 3）
   - 4つすべて検出されなければエラー

2. 描画エリア推定・パース補正
   - マーカーの内側の角から描画枠を計算
   - マーカー余白(insetMm)を考慮して描画枠コーナーを算出
   - 画像スケール(imageScale)に基づいて実際の画像領域を計算
   - バイリニア補間でパース補正し、4096x4096の正方形に変換

3. 背景色自動検出
   - 画像の四隅＋各辺中央の計8箇所からサンプリング（各50x50px）
   - 中央値ベースで外れ値に強い背景色推定
   - 検出結果はUIに表示

4. 前景/背景マスク生成
   - 各ピクセルについて以下の3条件で背景判定:
     a) 背景色との知覚的色差 < 閾値 (colorThreshold)
     b) エッジ（暗いピクセル）付近でない (edgeProtect)
     c) 保護色でない (肌色/カスタム色)
   - マスク: 白(255)=背景, 黒(0)=前景

5. ノイズ除去（モルフォロジカルオープニング）
   - 前景マスクに対して 収縮(erode) → 膨張(dilate) を適用
   - 小さな孤立前景ピクセル（スキャンノイズ）を除去
   - 半径以下のサイズの前景スペックが消える
   - 分離可能(水平→垂直)実装で高速処理

6. 外部/内部背景の判別（ギャップ閉じ処理付き）
   アルゴリズム（外部エロージョン＋再フラッドフィル方式）:

   Step 1: 初期フラッドフィル
     - 画像の縁(4辺)からBFSで背景ピクセルを辿り、外部背景を検出
     - 4方向接続（上下左右）

   Step 2: 外部エロージョン（収縮）
     - 検出した外部領域を gapCloseRadius 分収縮
     - 分離可能エロージョン（水平→垂直）
     - 細い通路（境界ギャップ経由で漏れた外部）が断ち切られる

   Step 3: 再フラッドフィル
     - 縁からエロージョン済み外部を通って再度BFS
     - 断ち切られた内部領域にはもう到達できない

   Step 4: 外部ダイレーション復元
     - エロージョンで縮んだ外部の端を元の背景範囲内でダイレーション
     - 外部と前景の境界が白くならないよう復元
     - isBackground制約付きダイレーション（前景を侵食しない）

7. カラーアルファ画像生成
   各ピクセルを3パターンに分類:
   - 外部背景（マスク=背景 かつ 外部） → 透明 (alpha=0)
   - 内部背景（マスク=背景 かつ 内部） → 白 (RGB=255, alpha=255)
   - 前景（マスク=前景）                → 元のカラーを保持 (alpha=255)

8. クロップ・出力
   - 不透明ピクセル(alpha>0)のバウンディングボックスを検出
   - 正方形にクロップし、5mmマージンを追加
   - PNGとしてダウンロード可能（単体/一括）

    : 外部領域を背景制約付きでダイレーション復元

  detectEdges(imageData, threshold) : 暗いピクセル検出＋周囲マーキング

  findColorBoundingBox(imageData)   : alpha>0のバウンディングボックス検出
  cropToSquareWithMargin(imageData, bbox, marginMm)
    : 正方形クロップ＋マージン付加
  downloadPng()                     : 単一ファイルダウンロード

--- バッチ処理 ---
  processAllFiles()                 : 選択全ファイルを順次処理
  loadImage(file)                   : FileをImage要素に変換（Promise）

  processImage(img)                 : マーカー検出→パース補正→カラー処理の統合

  reprocess()                       : パラメータ変更時の再処理

--- 2026-02-05: マーカー検出精度改善 ---

問題: スキャン画像によってはマーカーが検出されない（特に照明ムラ、ノイズ、
      低コントラストの場合）。特にID 0は内部パターンに大きな均一黒領域を持つ
      ため、適応二値化で検出困難。

原因:
  1. aruco2.jsのdetect()メソッドで使用される適応二値化パラメータが
     固定値（カーネル2, 閾値7）であり、画像条件に適合しない場合がある。
  2. ID 0の内部パターン（5x5中20セルが黒）には約150×190pxの均一黒領域が
     存在する。適応二値化の局所平均がこの領域内で非常に低くなり（~25）、
     閾値7を使うと brightness>18 のピクセルが白に誤判定される。
     黒セルの brightness が20-25のため、内部が白に化けて輪郭検出が破綻する。
     他のID（1,2,3）は白セルが分散しているため、この問題は発生しない。

解決:
  1. aruco2.jsのdetect()メソッドにoptionsパラメータを追加
     - adaptiveKernelSize: ボックスブラーのカーネル半径（デフォルト2）
     - adaptiveThreshold: 局所平均との差の閾値（デフォルト7）
     - useGlobalThreshold: trueの場合、適応二値化の代わりに大津二値化を使用
     - 後方互換性あり（optionsなしの呼び出しは従来と同じ動作）

  2. グローバル大津二値化の追加
     - CV.otsu()で画像全体のヒストグラムから最適閾値を算出
     - 適応二値化が失敗するケース（大きな均一黒領域）に対応
     - 画像全体の明暗分布に基づくため、局所平均の問題が発生しない
     - 全Phaseで適応二値化の試行後にOtsu二値化を試行

  3. detectMarkersWithPreprocessing()を大幅強化
     - 4セットの適応二値化パラメータ + 大津二値化を試行:
       (k=2,t=7): デフォルト（5×5ウィンドウ）
       (k=4,t=10): 中カーネル（9×9, 軽い照明ムラに対応）
       (k=7,t=15): 大カーネル（15×15, 強い照明ムラに対応）
       (k=10,t=20): 特大カーネル（21×21, 角の暗い影に対応）
       Otsu: グローバル二値化（大きな均一黒領域を持つマーカーに対応）
     - 6種類の前処理方法（キャッシュ付き遅延計算）:
       元画像 / コントラスト強調 / シャープ化 / コントラスト+シャープ /
       ブラー(1px) / ブラー+コントラスト
     - 試行順序: パラメータ優先（まず全前処理をデフォルトで試し、
       見つからなければパラメータを変更して再試行、最後にOtsu）
     - ダウンスケール・コーナー検出でも同様の二値化手法を試行

  4. マーカー統合検出機能
     - 各IDの最良検出結果を全試行にわたって保持
     - 異なる試行からのマーカーを統合（例: 適応二値化で ID 1,2,3、
       Otsu二値化で ID 0 を検出 → 統合して全4マーカー検出成功）
     - ハミング距離が最小の検出結果を各IDで採用
     - 二値化手法が異なるIDに効果的な場合に威力を発揮

  5. コーナー領域個別検出（Phase 3）
     - Phase 1,2 で全4マーカーが検出できなかった場合に実行
     - 未検出IDに対応するコーナー領域（画像の35%サイズ）を切り出し
     - コーナー画像に対して個別に前処理×パラメータ（適応+Otsu）を試行
     - 検出座標はフル画像座標系に変換して統合

  6. blurImage()関数を追加
     - Canvas filterによるガウシアンブラー
     - スキャンノイズの低減に効果的

3段階の検出パイプライン:
  - Phase 1a: 前処理6種 × 適応パラメータ4セット = 最大24回（適応二値化）
  - Phase 1b: 前処理6種 × Otsu = 最大6回（グローバル二値化）
  - Phase 2: スケール3種 × 前処理2種 ×（適応4セット+Otsu）= 最大30回
  - Phase 3: 未検出コーナー × 前処理3種 ×（適応4セット+Otsu）
  - 全段階でマーカー統合検出により、4マーカーが揃った時点で即座に終了


--- 2026-02-05: 閉じた領域の白背景対応 ---

要望: 色で囲まれた閉じた領域の内部背景を、透明ではなく白にしたい。

実装:
  - findExteriorPixels関数を追加（画像縁からBFSフラッドフィル）
  - 背景ピクセルを「外部背景」と「内部背景」に分類
  - 外部背景 → 透明(alpha=0)
  - 内部背景 → 白(RGB=255, alpha=255)
  - 前景 → 元のカラーを保持

初期実装は前景のダイレーション(膨張)でギャップを塞いでからフラッドフィル
する方式だったが、小さい閉じた領域で問題が発生。


--- 2026-02-05: ギャップ閉じアルゴリズム改善 ---

問題: 小さい閉じた領域が、ギャップ閉じ半径をどれだけ調整しても
      閉じた領域として認識されない。
      前景ダイレーション方式では、マスクの微小なギャップからフラッドフィルが
      漏れてしまい、小さな領域全体が外部扱いになる。

解決: アルゴリズムを「前景ダイレーション方式」から
      「外部エロージョン＋再フラッドフィル方式」に変更。

旧方式（前景ダイレーション）:
  1. 前景マスクをダイレーション（ギャップを塞ぐ）
  2. ダイレーション済みマスクでフラッドフィル
  問題点: 小さい領域ではダイレーションが効かない場合がある

新方式（外部エロージョン＋再フラッドフィル）:
  1. 元マスクでフラッドフィル（漏れを許容）
  2. 外部領域をエロージョン（細い漏れ通路を断ち切る）
  3. 縁からエロージョン済み外部を通って再フラッドフィル
     → 断ち切られた領域には到達不可 → 内部扱い
  4. エロージョンで縮んだ外部端をダイレーションで復元
  利点: 漏れた後に通路を断ち切るので、小さな領域でも確実に機能

UIスライダー追加: 「ギャップ閉じ半径」(デフォルト8px, 0〜50)


--- 2026-02-05: 背景ノイズ除去 ---

問題: 背景部分にスキャン由来の小さなノイズ（前景と誤判定されたスペック）が
      残っている。

解決: マスク生成後にモルフォロジカルオープニング（収縮→膨張）を適用。
  - 収縮で小さな孤立前景ピクセルを消去
  - 膨張で本来の前景を元のサイズに復元
  - 分離可能（水平→垂直の2パス）実装で4096x4096画像でも高速

UIスライダー追加: 「ノイズ除去」(デフォルト6px, 0〜10)
  - 大きいほど強力だが、細い線が消える可能性あり


================================================================================
■ アルゴリズム詳細: 分離可能モルフォロジカル演算
================================================================================

erodeArray / dilateArray は共通の高速手法を使用:
  - 水平パス（各行に対して左→右、右→左の2スイープ）
  - 垂直パス（各列に対して上→下、下→上の2スイープ）
  - 計算量: O(width * height) - 半径に依存しない

エロージョンの仕組み（erodeArray）:
  - 「最後に見た非対象ピクセル」の位置を追跡
  - 現在位置との距離が radius を超えている場合のみ生存
  - 左→右と右→左の両方で生存したピクセルのみ残す（AND条件）

ダイレーションの仕組み（dilateArray）:
  - 「最後に見た対象ピクセル」の位置を追跡
  - 現在位置との距離が radius 以内なら対象にする
  - 左→右と右→左の結果をOR結合

dilateToOriginal:
  - dilateArrayと同じロジックだが、isBackground制約付き
  - 背景ピクセルのみにダイレーション結果を適用（前景を侵食しない）


================================================================================
■ 既知の制限・注意点
================================================================================

- 閉じた領域の判定: ほぼ閉じている領域は白背景になるが、完全には白に
  ならない箇所が残る場合がある（alpha は抜かれないので実用上問題なし）
- ノイズ除去半径を大きくしすぎると、細い線画が消える可能性がある
- 出力サイズは固定 4096x4096（クロップ前）
- マーカーは ArUco辞書の ID 0〜3 を使用、4つすべて必要
- 画像スケールはテンプレート生成時と同じ値に設定する必要がある


--- 2026-02-07: マーカー検出の重複カウントバグ修正 ---

問題: FurukawaNaoki.png で ID 0 が検出されない。
      デフォルトパラメータ（k=2, t=7）で ID 1 が2回検出され、
      [1, 1, 2, 3] の4マーカーを検出。foundValidMarkers.length >= 4 の
      条件で早期返却され、ID 0 が未検出のまま処理終了していた。

原因:
  tryDetect() と tryScaledDetect() で「有効マーカー数」を
  foundValidMarkers.length（重複含む総数）でカウントしていた。
  重複マーカーがあると、ユニークID数が足りなくても条件を満たしてしまう。

解決:
  1. countUniqueValidIds() 関数を追加
     - new Set(markers.map(m => m.id)).size でユニークID数を算出
     - 重複マーカーを除外した正確なカウント

  2. deduplicateMarkers() 関数を追加
     - 各IDについてハミング距離が最小の検出結果のみを保持
     - 重複を除去して返却

  3. tryDetect() と tryScaledDetect() の修正
     - foundValidMarkers.length → uniqueIds.size に変更
     - 返却前に deduplicateMarkers() で重複除去
     - ログ出力も「ユニークID数」を表示するよう変更

検証:
  test_detect.js を作成し、全26画像で一括テストを実施。
  - FurukawaNaoki.png: adaptive(k=4,t=10) で全4ID検出成功
  - 他25画像: adaptive(k=2,t=7) で全4ID検出成功（既存動作に影響なし）
  - 結果: 26/26 OK, 0 FAIL


--- 2026-02-07: 背景色差閾値パラメータ調整 ---

変更:
  - 最小値: 10 → 1 に変更（より細かい調整が可能に）
  - デフォルト値: 50 → 20 に変更（背景除去をより厳密に）

理由:
  デフォルト50では背景に近い薄い色も除去されすぎる場合がある。
  閾値を小さくすることで、背景色と非常に近い色だけを透明化できる。
